## 1. Что известно о формате (Glassdoor, анекдотично)

- Раунд: pair programming на Java, дают готовый класс/скелет с методами, которые нужно дописать.
- Встречалась задача на circuit breaker (ООП-скелет с плейсхолдерами).
- Оценивают: знаком ли паттерн, предлагаешь ли несколько подходов, как общаешься с интервьюером, как думаешь вслух. Не алгоритмические головоломки, а ООП-дизайн и структуры данных.
- Часто есть теоретические вопросы «что будет, если...».

## 2. Рабочий процесс на раунде (главное)

1. **Одна фраза о роли компонента**: «Правильно понимаю, что этот класс вызывается из X, чтобы обеспечить Y, а `param` это просто Z?»
2. **Уточняющие вопросы** (объём, частота, что важнее, поведение при сбое).
3. **2 подхода, выбор, обоснование.** Без кода.
4. **Диагноз прежде лекарства**: сначала сценарий поломки по шагам, потом синхронизация.
5. **Код с комментариями по ходу.** Тест первым, если получается.
6. **Перечитать написанное вслух** до слов «готово».
7. Не подставлять похожий по звучанию термин. Не уверен, спроси.

## 3. Мои типичные ошибки (ловятся перечитыванием)

- Вычислил значение и не присвоил (`threshold`, `clock`, шаги `normalize`). Строки в Java неизменяемы.
- Опечатки: `Objects.requireNonNull`, `toCharArray()`, `replaceAll`.
- `requireNonNull` на примитивах бессмысленна: для чисел проверять диапазон.
- Единицы времени (мс против секунд).
- Один источник времени в методе: `clock.instant()` один раз.
- Подмена понятий: rate limiter принял за mutex, idempotency за «повтор действия», токен за объект с UUID.

## 4. Задача A: Circuit Breaker

**Терминология**: CLOSED = цепь замкнута, вызовы идут. OPEN = разомкнута, быстрый отказ (`CircuitOpenException`). HALF_OPEN = пробный вызов.

| Состояние | Поведение |
|---|---|
| CLOSED, успех | результат, счётчик сбоев в 0 |
| CLOSED, сбой | исходное исключение, счётчик +1; порог достигнут -> OPEN |
| OPEN | отказ сразу; после `openTimeout` -> HALF_OPEN |
| HALF_OPEN, проба ок | -> CLOSED |
| HALF_OPEN, проба упала | -> OPEN, новый таймер |

**Ключевые решения**
- Лок только на короткие переходы (`beforeCall` / `onSuccess` / `onFailure`), `supplier` выполняется **вне лока**. Иначе один медленный downstream ставит всех в очередь и fail fast пропадает.
- Одна проба в HALF_OPEN: захватывается атомарно в `beforeCall`, остальные получают отказ.
- **generation**-счётчик: результат вызова, начатого до последнего перехода, игнорируется. Лучше инкрементировать в одном `transitionTo(state)`.
- `catch (Exception | Error e)`, чтобы состояние не застряло в HALF_OPEN.
- Часы через `Clock`, тесты с `MutableClock` (`getZone`, `withZone`, `instant`, `advance`), без `Thread.sleep`.
- `ThrowingSupplier<T>`: не терять checked-исключения.

**Ответы на вопросы интервьюера**
- Зависшая проба: таймаут принадлежит транспортному уровню (HTTP read timeout, JDBC `queryTimeout`, pool `connectionTimeout`); `Future.cancel(true)` не гарантирует прерывание. Breaker считает таймаут сбоем. Дополнительно можно хранить дедлайн пробы + generation.
- Подряд идущие сбои против процента: скользящее окно и порог по проценту как развитие.
- Одна проба против нескольких: проще и безопаснее для больного сервиса; в Resilience4j настраивается.
- Формулировка: «Circuit breaker меняет медленный отказ на быстрый и защищает обе стороны».
- enum+switch против State pattern: для 3 состояний enum нормален; паттерн окупается при росте числа состояний и правил.

## 5. Задача B: Name Screener (санкционные списки)

**Архитектура**: candidate generation (дешёвый индекс) + scoring (дорогой matcher).

- Конструктор строит **инвертированный индекс триграмм** один раз: `Map<String, Set<Integer>>` (триграмма -> индексы сущностей). Индексируются `fullName` и все алиасы.
- `screen()`: триграммы клиента -> кандидаты со счётчиком пересечений -> отсев по `MIN_TRIGRAM_OVERLAP` -> `NameMatcher.similarity()` только на кандидатах -> максимум по имени/алиасам/matcher'ам -> фильтр по `threshold` -> сортировка по убыванию.
- `NameMatcher`: `double similarity(String a, String b)` в [0, 1]. Расширяемость через Strategy (exact, без порядка слов, fuzzy: Jaro-Winkler/Levenshtein).
- `normalize`: NFD -> убрать `\p{M}` -> `toLowerCase(Locale.ROOT)` (турецкая `I`) -> `[^\p{L}\p{N}]+` в пробел -> trim. Для порядка слов: отсортировать токены.
- Обновление списка: строим новый `NameScreener`, атомарно подменяем ссылку (`AtomicReference`/`volatile`). Список обновляется раз в день, инкрементальность не нужна.
- Иммутабельность после конструктора -> потокобезопасность без блокировок (`List.copyOf`).

**Про пороги (связь с precision/recall)**: в реальных системах два порога: выше верхнего -> автоблок, между -> ручная проверка аналитиком, ниже нижнего -> пропуск. Нижний порог управляет recall (не пропустить нарушителя), верхний управляет ложными блокировками. Пропустить нарушителя хуже, но поток ложных срабатываний парализует аналитиков.

**Граф связей** (Neo4j/GraphRAG) относится к другому уровню: цепочки владения, связанные лица. К сравнению имён не относится.

**Мелочи на вопросы**: `Integer` против `int` в HashMap (unboxing), вынести `normalize/trigrams` в `NameNormalizer`, частые триграммы -> требовать минимум общих.

## 6. Задача C: Token Bucket Rate Limiter

**Роль**: `tryAcquire(clientId)` отвечает «разрешить ли клиенту ещё один запрос сейчас». Защита сервиса от слишком частых запросов. Не mutex.

- **Токен это число, а не объект.** `double tokens`, как баланс на счету. Дробное, потому что `refillTokensPerSecond` это скорость: за 137 мс при 5/сек накапливается 0.685.
- `capacity` = разрешённый всплеск. `refillTokensPerSecond` = установившийся темп. Оба в конструкторе (политика), в метод передаётся только `clientId`.
- **Ленивое пополнение**: при каждом вызове `elapsed = now - lastRefill`, `tokens = min(capacity, tokens + elapsed * rate)`. Не нужен фоновый поток, точность не зависит от тика, неактивные клиенты не стоят ресурсов.
- `Map<String, Bucket>` как `ConcurrentHashMap` + `computeIfAbsent`. Обычный `HashMap` при параллельных `put` может испортить внутреннюю структуру (цикл в списке, зависание).
- **Диагноз гонки внутри Bucket**: два потока читают устаревшее `tokens`, оба списывают, оба возвращают `true` (lost update) -> лимитер пропускает больше разрешённого. Лечение: `synchronized` на объекте `Bucket`.
- **Почему здесь лок на весь расчёт, а в CircuitBreaker нет**: внутри лока только арифметика (наносекунды), нет I/O и чужого кода. Критерий: «что внутри лока, может ли оно зависнуть?»
- Новый клиент стартует с полным ведром (первый легитимный запрос не отклоняется).
- Защиты: `Math.max(0, elapsed)` при откате часов; `clock.instant()` брать внутри синхронизированного метода (или обновлять `lastRefill` только вперёд); валидация `capacity > 0`, `rate > 0`.
- Память: `buckets` только растёт -> чистка давно полных ведер или Caffeine `expireAfterAccess`.

```java
synchronized boolean tryConsume(int capacity, double ratePerSec, Instant now) {
    double elapsed = Duration.between(lastRefillTime, now).toNanos() / 1e9;
    tokens = Math.min(capacity, tokens + Math.max(0, elapsed) * ratePerSec);
    if (now.isAfter(lastRefillTime)) lastRefillTime = now;
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
}
```

## 7. Задача D: Idempotent Processor

**Роль**: гарантирует, что действие для данного `idempotencyKey` выполнится **не более одного раза** в пределах TTL; повторы получают результат первого выполнения. (Он не повторяет действие сам.)

- **TTL** = время жизни записи. Проверка через `Clock`. Нужен, чтобы Map не рос бесконечно и чтобы «повтор через неделю» считался новым запросом.
- `Entry`: `CompletableFuture<R> future` (состояние «идёт/готово») + `expiresAt` + отпечаток тела запроса.
- **Владелец против повтора**: `putIfAbsent` возвращает `null` -> ты владелец. `computeIfAbsent` этого не различает. `action.get()` выполняется **вне** блокировки Map.
- **Гонка наивного «containsKey, потом put»**: два потока оба не видят ключ, оба выполняют действие -> дубль платежа.
- При сбое владельца: `entries.remove(key, mine)` **до** `completeExceptionally`, чтобы новый повтор не увидел уже проваленную запись. Политика: упавшая попытка не блокирует ключ.
- Повтор ждёт `future.get(timeout)`; по таймауту `RequestInProgressException` (в REST 409). Без таймаута `join()` подвесит потоки при зависшем владельце.
- **TTL-протухание только для завершённых записей**: `future.isDone() && !now.isBefore(expiresAt)`. Иначе долгое действие вытеснится, и платёж выполнится дважды. `remove(key, existing)` + `continue` в цикле; проигравший в `remove` просто идёт на новый круг.
- Другое тело запроса с тем же ключом: хранить **fingerprint** (хеш, например SHA-256) **первого** запроса, не payload (размер, PII). Ошибка 422 (409 оставляем для «в обработке»).
- Вариант при падении владельца: ожидающий повтор идёт на новый круг и сам становится владельцем (с ограничением числа кругов).
- Чистка записей, к которым не обращаются: периодический `removeIf` или кэш с истечением.

**Тесты (MutableClock, без sleep)**: один ключ выполнен один раз; упавшее действие освобождает ключ; сдвиг за TTL и граница; зависший владелец на `CountDownLatch` -> таймаут; действие дольше TTL не вытесняется; разные ключи независимы.
